# Phase 11 - Multiple Policies (PERMISSIVE Behavior)

## Objective

Understand how PostgreSQL combines multiple Row Level Security policies applied to the same table and operation.

This phase demonstrates one of the most important RLS concepts:

```text

Multiple policies are not automatically combined using AND.

By default, PostgreSQL combines policies using OR.

```

This behavior can significantly impact tenant isolation if not fully understood.

## Background

At the beginning of this phase, the patients table contained:

```text

Tenant A
→ João Silva

Tenant B
→ Maria

```

The existing SELECT policy was:

```sql

CREATE POLICY patients_by_tenant
ON patients
FOR SELECT
TO app_user, migration_user
USING (
tenant_id =
current_setting('app.tenant_id')::uuid
);

```

Assuming a Tenant A session:

```sql

SET ROLE app_user;

SET app.tenant_id =
'813d31c5-5116-4fea-b4b8-eb06ce7e773c';

```

The query:

```sql

SELECT *
FROM patients;

```

returned:

```text

João Silva

```

because only Tenant A data was visible.

## Initial Hypothesis

Before executing the experiment, the assumption was:

```text

Policy 1:
tenant_id = current tenant

Policy 2:
name = 'Maria'

Expected behavior:

Policy 1
AND
Policy 2

```

Under this assumption, no rows would match because Maria belongs to Tenant B.

## Create a Second SELECT Policy

Create an additional policy:

```sql

CREATE POLICY patients_maria_access
ON patients
FOR SELECT
TO app_user
USING (
name = 'Maria'
);

```

At this point two SELECT policies existed for app_user.

## Experiment

Execute:

```sql

SELECT *
FROM patients;

```

Result:

```text

                  id                  |              tenant_id               |    name    
--------------------------------------+--------------------------------------+------------
 f241beeb-1f80-4059-8643-fabd1d7a4214 | f46c8eb7-4b1b-4ba6-8f53-734edf04d328 | Maria
 cfb6ceaf-6fbf-4174-ac84-a877cb19262a | 813d31c5-5116-4fea-b4b8-eb06ce7e773c | João Silva
(2 rows)

```

Unexpectedly, both rows became visible.

## Execution Plan Analysis

Execution plan:

```sql

EXPLAIN ANALYZE
SELECT *
FROM patients;

```

Result:

```sql

                                                 QUERY PLAN                                                 
------------------------------------------------------------------------------------------------------------
 Seq Scan on patients  (cost=0.00..13.15 rows=2 width=548) (actual time=0.018..0.023 rows=2 loops=1)
   Filter: (((name)::text = 'Maria'::text) OR (tenant_id = (current_setting('app.tenant_id'::text))::uuid))
 Planning Time: 0.132 ms
 Execution Time: 0.048 ms
(4 rows)

```

### Observation

The execution plan clearly shows PostgreSQL combining both policies using:

```text

OR

```

instead of:

```text

AND

```

## What PostgreSQL Did

Policy 1:

```sql

tenant_id =
current_setting('app.tenant_id')::uuid

```

Policy 2:

```sql

name = 'Maria'

```

Effective condition generated by PostgreSQL:

```sql

(
tenant_id =
current_setting('app.tenant_id')::uuid
)
OR
(
name = 'Maria'
)

```

As a result:

```text

João Silva
→ Visible because Tenant A

Maria
→ Visible because name = 'Maria'

```

## Understanding PERMISSIVE Policies

By default, PostgreSQL creates policies as:

```text

PERMISSIVE

```

PERMISSIVE policies are combined using:

```text

OR

```

This means each new policy creates an additional path that grants access.

Conceptually:

```text

Policy A
OR
Policy B
OR
Policy C

```

A row becomes visible if any policy returns TRUE.

## Why This Is Important

Many developers intuitively expect:

```text

# More policies

More restrictions

```

However, with PERMISSIVE policies:

```text

# More policies

More ways to gain access

```

This distinction is critical in multi-tenant systems.

## Real-World SaaS Example

Suppose a SaaS application already contains:

```sql

tenant_id =
current_setting('app.tenant_id')::uuid

```

Later, another policy is added:

```sql

is_support = true

```

A developer might assume:

```text

Tenant filter
AND
Support filter

```

But PostgreSQL actually evaluates:

```text

Tenant filter
OR
Support filter

```

This can dramatically expand data visibility.

## Inspecting Policies

Policies can be inspected through:

```sql

rls_lab=> SELECT
    policyname,
    permissive
FROM pg_policies
WHERE tablename = 'patients';


        policyname         | permissive 
---------------------------+------------
 patients_by_tenant        | PERMISSIVE
 patients_insert_by_tenant | PERMISSIVE
 patients_update_by_tenant | PERMISSIVE
 patients_delete_by_tenant | PERMISSIVE
 patients_maria_access     | PERMISSIVE
(5 rows)

```

The permissive column reveals how PostgreSQL classifies the policy.

## Key Learnings

* Multiple policies are not automatically combined using AND.
* PostgreSQL creates policies as PERMISSIVE by default.
* PERMISSIVE policies are combined using OR.
* Every additional PERMISSIVE policy creates another access path.
* Query plans clearly expose how PostgreSQL combines policies.
* Incorrect assumptions about policy composition can lead to security issues.
* Understanding policy composition is essential for SaaS architectures.

## Concepts Learned

```text

Single Policy
→ Single access path

Multiple PERMISSIVE Policies
→ OR behavior

Policy A
OR
Policy B
OR
Policy C

More policies
≠
More restrictions

# More policies

More access paths

```

This phase demonstrates one of the most important PostgreSQL RLS behaviors and prepares the foundation for the next topic:

```text

RESTRICTIVE Policies

```

where PostgreSQL can be instructed to combine policies using AND instead of OR.
